# 평가 하네스

레이블된 코퍼스로 스캐너의 precision / recall / F1 을 측정한다.

```bash
go run ./eval                  # 정확도 측정 (precision / recall / F1)
go run ./eval --coverage       # 어떤 룰이 검증되고 있는지 확인
go run ./eval --history        # git 히스토리 스캔 시나리오 평가
go run ./eval --tool gitleaks  # gitleaks 측정 (설치 필요)
go run ./eval --markdown       # 마크다운 표로 출력
```

## 구성

| 경로 | 내용 |
|---|---|
| `_corpus/` | 평가용 가짜 프로젝트. 실제 시크릿과 오탐 유발 케이스가 섞여 있다 |
| `labels.yaml` | 정답 레이블. 어떤 줄이 진짜 시크릿인지 기록 |
| `history.yaml` | 히스토리 스캔 시나리오. 커밋 순서와 기대 결과를 정의 |
| `main.go`, `history.go` | 측정 러너 |

> 디렉토리 이름이 `_corpus` 인 이유: Go 툴체인은 `_` 로 시작하는 디렉토리를 무시한다.
> 코퍼스에는 컴파일되지 않는 가짜 Go 파일이 있어, 그러지 않으면 `go build`/`go vet`/`go test`가 전부 깨진다.

## 채점 방식

- 채점 단위는 **(파일, 줄)** 이다. 한 줄에서 여러 룰이 걸려도 1건으로 센다.
  도구가 같은 줄을 중복 보고한다고 불리해지지 않게 하기 위함이다.
- 이 방식은 **어떤 종류로 분류했는지를 보지 못한다.** 시크릿을 찾았지만 엉뚱한 룰로 잡아
  심각도가 낮게 나가도 TP로 계산된다. 그래서 레이블의 `kind`와 실제 룰 ID를 비교해
  **오분류**를 따로 집계한다 (precision/recall 에는 반영하지 않는다).
  룰 ID 체계는 도구마다 달라 secrethound 측정 시에만 확인한다.
- `labels.yaml`의 `secrets`에 없는 모든 줄은 음성으로 간주한다.
- `traps`는 채점에 직접 쓰이지 않는다. 어떤 오탐 케이스를 의도적으로 넣었는지
  문서화하고, 오탐 발생 시 사유를 함께 출력하기 위한 기록이다.
- 하네스는 코퍼스의 모든 파일이 레이블에 등재되어 있는지 검증한다.
  레이블이 누락된 파일이 있으면 그 파일의 탐지가 조용히 오탐으로 잡혀 수치가 왜곡되기 때문이다.

측정 대상은 CLI와 **동일한 파이프라인**(`internal/scanner`)이다.
하네스가 스캔 로직을 따로 구현하면 실제 제품이 아닌 다른 것을 측정하게 된다.

### 시크릿 판정 기준

- 공개되도록 설계된 값(Stripe publishable key, Google OAuth Client ID, SRI 무결성 해시,
  Sentry DSN)은 **유출이 아니므로 시크릿이 아니다**. 탐지하면 오탐으로 센다.
- 형식만 맞고 값이 플레이스홀더/더미인 경우도 시크릿이 아니다.

## 룰 커버리지

정확도 수치는 **코퍼스에 케이스가 있는 룰에 대해서만** 의미가 있다.
한 번도 발동하지 않은 룰은 정규식이 틀려도 알 수 없으므로, 커버리지를 따로 추적한다.

```
룰 커버리지: 30 / 30
```

판정 기준은 "최종 결과에 나타났는가"다. 매칭은 됐지만 오탐 필터나 중복 제거로 사라진 룰은
사용자에게 도달하지 않으므로 검증된 것으로 보지 않는다.
이 기준 덕분에 `stripe-test-key` 룰이 **구조적으로 도달 불가능**하다는 것이 드러났다
(값에 `test` 가 들어가 플레이스홀더 감점에 항상 걸린다). 해당 룰은 제거했다.

## 히스토리 스캔 평가

`history.yaml` 에 정의한 커밋 순서대로 임시 git 레포를 만들어,
워킹트리 스캔과 `--history` 스캔 결과를 각각 채점한다.

| 시나리오 | 워킹트리 | `--history` |
|---|:---:|:---:|
| 커밋했다가 지운 토큰 | 미탐지(정상) | 탐지 |
| 파일째 삭제된 모듈의 AWS 키 | 미탐지(정상) | 탐지 |
| 현재도 남아있는 Stripe 키 | 탐지 | 탐지 |

## 측정 결과

코퍼스: 실제 시크릿 45건, 오탐 유발 케이스 34건

| 시점 | Precision | Recall | F1 | 룰 커버리지 |
|---|---:|---:|---:|---:|
| 초기 | 0.765 | 1.000 | 0.867 | 13 / 31 |
| 오탐 수정 후 | 1.000 | 1.000 | 1.000 | 13 / 31 |
| 코퍼스 확장 직후 | 1.000 | 0.875 | 0.933 | — |
| 국내 룰셋 추가 전 | 1.000 | 1.000 | 1.000 | 29 / 29 |
| 최종 | 1.000 | 1.000 | 1.000 | 37 / 37 |

세 번째 행이 중요하다. 룰 커버리지를 채우려고 **실제 코드에 쓰이는 표기 그대로**
케이스를 추가했더니 recall 이 1.000에서 0.875로 떨어졌다.
정규식에 맞춰 코퍼스를 쓰면 검증이 아니라 자기 확인이 되므로, 실제 표기를 우선했다.

### 하네스가 찾아낸 문제와 조치

| 오탐 | 원인 | 조치 |
|---|---|---|
| `pk_live_...` (2건) | Stripe publishable key 룰이 공개 설계값을 보고 | 룰 삭제 |
| `...apps.googleusercontent.com` | Google OAuth Client ID 룰이 공개 식별자를 보고 | 룰 삭제 |
| `postgresql://user:password@localhost:5432/dev` | `.env.example` 경로 감점(-50)이 임계값(50)에 정확히 걸려 통과 | `@localhost` 등 로컬 엔드포인트 감점 룰 추가 |

세 번째 항목은 경로 감점을 올리는 대신 **로컬 엔드포인트**라는 일반적인 신호를 쓰도록 고쳤다.
`.env.example` 이 아닌 곳에 있는 개발용 접속 문자열에도 동일하게 적용되기 때문이다.

### 수치에 잡히지 않던 오분류

`terraform/main.tf:4` 의 AWS 시크릿 키는 탐지는 되었지만 `generic-api-key`(medium)로 분류되어
실제 심각도인 critical 보다 두 단계 낮게 보고되고 있었다.
채점이 (파일, 줄) 단위라 TP로 집계되어 **precision/recall 로는 드러나지 않던 결함**이다.

| 원인 | 조치 |
|---|---|
| HCL의 `secret_key = "..."` 는 줄에 `aws` 문자열이 없어 AWS 전용 룰이 매칭되지 않음 | `aws-secret-access-key-bare` 룰 추가 (길이 40 base64 + 엔트로피 4.2로 한정) |
| 구체적 룰과 범용 룰이 같은 값을 동시에 보고 | 같은 (파일, 줄, 값, 커밋)이면 심각도 높은 쪽만 남기는 중복 제거 추가 |
| 하네스가 분류 오류를 보지 못함 | 레이블의 `kind`와 실제 룰 ID를 비교하는 오분류 집계 추가 |

### 코퍼스 확장으로 드러난 미탐 4건

실제 코드에 쓰이는 표기를 그대로 옮겼더니, 룰이 그 표기를 따라가지 못하는 경우가 나왔다.

| 놓친 것 | 원인 | 조치 |
|---|---|---|
| `aws_secret_access_key = <값>` | `~/.aws/credentials` 는 INI 형식이라 값에 따옴표가 없는데 룰이 따옴표를 필수로 요구 | 따옴표를 선택적으로 변경. 대신 40자 뒤에 경계를 둬 더 긴 토큰의 일부를 잘라 잡는 것을 방지 |
| `aws_session_token = <값>` | 같은 원인 | 같은 조치 |
| `HEROKU_API_KEY=<UUID>` | `heroku` 바로 뒤에 비영숫자만 허용해 `_API_KEY` 를 넘지 못함 | `api`/`key` 단어가 이어지는 형태 허용 |
| `discordBotToken: "<값>"` | 같은 원인 (camelCase 변수명) | `bot`/`token` 단어가 이어지는 형태 허용 |

`TWILIO_API_KEY=` 도 같은 결함이 있어 함께 고쳤다.

### 레이블 자체의 오류

gitleaks 비교 과정에서 **내가 만든 정답이 틀린 것**도 발견했다.
`config/gcp-service-account.json` 의 `"type": "service_account"` 줄을 시크릿으로 레이블하고
전용 룰을 두고 있었는데, 이 줄은 파일 종류 표시일 뿐 자격증명이 아니다.
자기 룰에 맞춰 정답을 만든 셈이라 룰과 레이블을 모두 되돌렸다.
이 파일의 실제 시크릿인 `private_key` 필드는 `private-key` 룰이 이미 잡는다.

### 고치지 않고 한계로 남긴 것

`twilio: { apiKey: "SK..." }` 처럼 **키 이름과 값이 다른 줄에 있으면** 벤더 특정 룰이 매칭되지 않는다.
줄 단위 스캔의 구조적 한계다. 값 자체(`SK` + 32 hex)만으로는 시크릿이라 단정할 수 없어
컨텍스트 요구를 유지했고, 범용 룰이 대신 잡아낸다(탐지는 되지만 심각도가 medium).

측정 과정에서 코퍼스 자체의 오류도 2건 발견해 수정했다
(GitLab PAT 19자 → 20자, SendGrid 키 44자 → 43자. 둘 다 실제 형식과 달랐다).

## gitleaks 비교

동일 코퍼스, 동일 채점 기준으로 측정했다 (gitleaks v8.30.1).

| 도구 | Precision | Recall | F1 | TP | FP | FN |
|---|---:|---:|---:|---:|---:|---:|
| secrethound | 1.000 | 1.000 | 1.000 | 32 | 0 | 0 |
| gitleaks | 0.875 | 0.875 | 0.875 | 28 | 4 | 4 |

**이 표를 "secrethound가 더 낫다"로 읽으면 안 된다.** 비교는 구조적으로 이쪽에 유리하다.

- 코퍼스를 내가 만들었고, 내 룰을 이 코퍼스에 맞춰 고쳤다. gitleaks는 그런 기회가 없었다.
- 코퍼스에 넣을 서비스를 **내 룰셋이 지원하는 것 위주로 골랐다.**
  gitleaks 미탐 4건 중 3건은 "룰이 틀렸다"가 아니라 "기본 룰셋에 그 서비스가 없다"이다.
- 오탐 4건 중 2건(Stripe 테스트 키, 공개 JWT)은 **판정 기준의 차이**다.
  gitleaks는 위생 차원에서 보고하는 쪽을 택했고, 나는 유출 피해가 없으면 시크릿이 아니라고 봤다.

### 그래도 의미 있는 관찰

| gitleaks 결과 | 성격 |
|---|---|
| `~/.aws/credentials` 의 따옴표 없는 AKIA 키 미탐 | **양쪽 다 있던 결함.** 이 케이스를 코퍼스에 넣기 전에는 secrethound도 놓쳤다 |
| DB 접속 문자열, Anthropic 키, Basic 인증 헤더 미탐 | 기본 룰셋의 범위 차이. 코퍼스 구성에 좌우되는 항목 |
| Stripe publishable key 오탐 (2건) | 공개되도록 설계된 값을 보고. 판정 기준 차이지만 노이즈라는 데는 대체로 동의할 만하다 |
| 문서용 JWT(서명이 `dummy_...`) 오탐 | 플레이스홀더 감점이 실제로 효과를 낸 사례 |

공정하게 비교하려면 **제3자가 만든 코퍼스**가 필요하다. 현재 표는 그 전 단계의 참고 자료다.

## 실제 오픈소스 레포 스캔

자체 코퍼스 과적합 우려를 검증하려고, 잘 관리되는 공개 레포를 그대로 스캔했다.
시크릿이 거의 없어야 정상이므로, 나오는 것은 대부분 오탐으로 볼 수 있다.

| 레포 | 커밋 | 워킹트리 | 히스토리 포함 | 소요 |
|---|---:|---:|---:|---:|
| spf13/cobra | 992 | 0 | 0 | 311ms |
| sirupsen/logrus | 1,009 | 0 | 0 | 201ms |
| expressjs/express | 5,678 | 0 | 0 | 1,417ms |
| gin-gonic/gin | 1,791 | 1 | 2 | 495ms |
| pallets/flask | 3,824 | 3 | 12 → 3 | 2,118ms |
| **합계** | **13,294** | **4** | **14 → 5** | — |

> 화살표는 아래 "히스토리 중복 보고" 문제를 고친 뒤의 수치다.

탐지된 건들의 원인은 단 **2가지**였다.

| 원인 | 판정 | 비고 |
|---|---|---|
| Flask 문서의 예시 `SECRET_KEY` (`192b9b…`, `5f3523…`) | 오탐 | 문서에 실린 예시값. `docs/` 경로 감점으로 신뢰도 60까지 내려갔으나 임계값을 넘김 |
| gin의 테스트용 TLS 인증서 개인키 | 오탐 | `testdata/` 의 테스트 픽스처. 실제 키지만 의도적으로 커밋된 것 |

**과적합 우려에 대한 결론**: 잘 관리되는 레포 5개, 13,294개 커밋에서 오탐 원인이 2개뿐이었다.
자체 코퍼스에서만 잘 동작하는 상태는 아니라고 볼 근거가 생겼다.
다만 5개 레포는 여전히 작은 표본이고, 모두 시크릿이 거의 없는 성숙한 프로젝트라
**미탐(놓친 진짜 시크릿)은 이 방법으로 측정할 수 없다.**

### 여기서 드러난 문제: 히스토리 중복 보고

Flask의 12건은 실제로는 **서로 다른 값 2개**가 커밋과 줄 위치를 바꿔가며 반복된 것이다.

```
docs/config.rst:41                    192b9b******bcbf
docs/config.rst@58a08a1:41            192b9b******bcbf
docs/config.rst@58a08a1:471           192b9b******bcbf
docs/tutorial/deploy.rst:73           192b9b******bcbf
...
```

같은 값이 여러 커밋에 걸쳐 있으면 그만큼 행이 늘어난다.
실제로 유출된 키가 오래된 레포에 있으면 수십 줄로 불어나 리포트를 읽기 어려워진다.
현재 중복 제거는 (파일, 줄, 값, 커밋) 단위라 이 경우를 합치지 못한다.

**자체 코퍼스에서는 드러나지 않던 문제다.** 코퍼스의 히스토리 시나리오는 커밋이 3개뿐이라
같은 값이 여러 커밋에 반복되는 상황을 만들지 못했다.

#### 조치

같은 파일에 있는 같은 값을 하나로 묶고, 위치는 **최초 유입 시점**을 가리키게 했다.
유출 대응에서 정작 필요한 정보가 "언제 처음 들어왔는가"이기 때문이다.
파일이 다르면 묶지 않는다 — 같은 키가 여러 파일에 하드코딩됐다면 전부 찾아 지워야 한다.

```
MEDIUM  docs/config.rst@58a08a1:41   192b9b******bcbf  (신뢰도 60, 4곳, 현재도 존재)
MEDIUM  docs/config.rst@465922e:388  5f3523******5d2f  (신뢰도 60, 6곳)
MEDIUM  docs/tutorial/deploy.rst@58a08a1:101  192b9b******bcbf  (신뢰도 60, 2곳, 현재도 존재)
```

Flask 기준 12행 → 3행. 두 번째 값에 "현재도 존재"가 없는 것은 나중에 교체되어
워킹트리에는 남아있지 않다는 뜻이다. 폐기 우선순위를 판단할 때 필요한 구분이다.

## 이 숫자를 어떻게 읽어야 하나

**F1 1.000은 "이 도구가 완벽하다"는 뜻이 아니다.** 다음 한계를 전제로 읽어야 한다.

1. **자체 제작 코퍼스다.** 내가 생각해낸 케이스만 들어 있다.
   측정 결과는 "내가 예상한 상황을 처리하는가"이지 일반적인 성능이 아니다.
2. **같은 코퍼스를 보고 룰을 고쳤다.** 위 조치는 이 코퍼스에 대한 과적합이다.
   새로운 코퍼스에서는 점수가 떨어질 것이 거의 확실하다.
   실제로 코퍼스를 확장하자마자 recall 이 0.875로 떨어진 것이 그 증거다.
3. **규모가 작다.** 시크릿 45건은 통계적으로 유의미한 크기가 아니다.
   한 건만 틀려도 recall 이 0.97로 떨어진다.

따라서 현재 수치는 **회귀 방지용 기준선**으로 쓰는 것이 정확한 용도다.
룰을 고쳤을 때 기존 케이스가 깨지지 않는지 확인하는 장치이지,
다른 도구보다 우수하다는 근거가 아니다.
