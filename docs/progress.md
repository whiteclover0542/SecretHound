## MVP 제외 (이후 검토)

### Entropy Analyzer — 독립 탐지기
정규식 룰에 없는 미지의 시크릿을 엔트로피만으로 탐지하는 기능. **MVP에서 제외한다.**
- 제외 이유: 단독 엔트로피 탐지는 오탐이 급증해(해시값, UUID, base64 인코딩된 이미지,
  압축된 문자열 등이 전부 걸림) 임계값 튜닝에 드는 비용 대비 얻는 게 적다.
  현재는 룰별 `entropy` 임계값을 정규식 매칭의 **보조 검증**으로만 쓰는 편이 정확도가 높다.
- 이미 구현된 것: `detector.Shannon()` (룰별 엔트로피 게이트에서 사용 중)
- 나중에 한다면: base64/hex 문자셋 판별 → 문자셋별 임계값 → 정규식 룰과 중복 제거 순서

### PII(개인정보) 탐지 — 확장 룰셋
주민등록번호·전화번호·카드번호 등 **사람에 대한 정보**를 탐지하는 기능. **MVP에서 제외한다.**

- 현재 상태: `rules/default.yaml`의 32개 룰은 전부 머신 크리덴셜(API 키/토큰/개인키/DB 접속정보)이다.
  PII 룰은 하나도 없다.
- 제외 이유: MVP의 정의가 "시크릿 스캐너"이고 동종 도구(gitleaks/trufflehog)도 credential 전용이다.
  PII 탐지는 DLP라는 별개 카테고리라, 지금 섞으면 도구의 정체성과 오탐 기준이 함께 흐려진다.
- 붙이기 쉬운 이유: 룰이 YAML로 분리돼 있어 `config.Rule` 구조체를 건드리지 않고 정규식 룰만
  추가해도 동작한다. 전화번호·이메일·계좌번호 등은 정규식만으로 충분하다.

**선행 작업 2가지** (이게 없으면 오탐 때문에 못 쓴다)

1. **체크섬 validator 훅** — 주민등록번호(가중치 검증), 카드번호(Luhn)는 정규식만으로는 오탐이 심하고
   Go의 RE2는 백레퍼런스가 없어 정규식 안에서 해결이 불가능하다. `Penalty.Builtin`과 같은 방식으로
   `Rule`에 `validator` 필드를 추가해 코드 검증을 연결해야 한다.
2. **엔트로피 게이트 미적용** — PII는 랜덤 문자열이 아니라 엔트로피가 낮다. 룰의 `entropy` 필드를
   비우면 되지만 그만큼 FP Filter 부담이 커지므로, 더미 번호(`000-0000-0000`, `123-45-67890` 류)와
   테스트 픽스처 경로에 대한 감점 룰을 함께 넣어야 한다.

**설계 메모**

- 룰을 `pii` 태그로 묶고 `--tags pii` 로 옵트인. **기본 비활성**이 맞다.
  (크리덴셜 스캔만 원하는 사용자에게 PII 오탐을 강제로 보여줄 이유가 없다)
- 마스킹은 필수. 스캔 리포트에 주민번호가 그대로 찍히면 **리포트 자체가 유출 경로**가 된다.
  기존 `detector`의 마스킹 로직을 재사용하되 PII는 마스킹 비율을 더 높게 잡는다.

**체크리스트**

- [ ] `config.Rule`에 `validator` 필드 추가 + 검증 코드 구현 (`luhn`, `kr-rrn`)
- [ ] `rules/pii.yaml` 작성 — 주민등록번호, 휴대폰번호, 카드번호, 계좌번호, 이메일, 여권번호
- [ ] `--tags` / `--exclude-tags` 플래그로 룰 그룹 선택
- [ ] PII 전용 감점 룰 (더미 번호 패턴, 테스트 픽스처 경로)
- [ ] PII 강화 마스킹 + 리포트 출력 시 원본 노출 여부 점검

## 확장 로드맵 (차별화 근거 만들기)

**문제 인식**: 기획서의 차별화 포인트는 *"gitleaks/trufflehog 대비 오탐 감소"* 인데,
현재 그 주장을 **증명하는 근거가 없다**. FP Filter에 감점 룰을 넣었다는 사실만으로는
"실제로 오탐이 줄었는가"에 답할 수 없다. 분량이 부족한 게 아니라 주장에 근거가 비어 있는 상태.
아래는 깊이 대비 효율 순으로 정리한 확장 항목이다.

| 우선순위 | 항목 | 예상 | 목적 | 상태 |
|:---:|---|---|---|:---:|
| 1 | 키 유효성 검증 (Validator) | 2~3일 | 추정이 아니라 발급처 응답으로 위험 여부 판정 | ✅ |
| 2 | 평가 하네스 + 벤치마크 | 2일 | 차별화 주장에 숫자를 붙임 | ✅ |
| 3 | baseline 파일 | 1일 | 실무 도입 필수 기능 | ✅ |
| 4 | 병렬 스캔 + 성능 수치 | 1~2일 | Go 선택 이유(goroutine)의 정당화 | ✅ |
| 5 | remediation 안내 | 1일 | 탐지 이후 행동까지 연결 | ✅ |

**1 + 2만 붙여도 3~4주짜리 프로젝트가 되고, 성격이 "만들어봤다"에서
"기존 도구의 약점을 측정하고 개선했다"로 바뀐다.**

#### 1. 키 유효성 검증 (Validator) — 완료

**문제였던 것**: 탐지된 키를 실제 API에 최소 권한으로 호출해 살아있는지 확인하는
기능인데, 처음 구현할 때 발급처의 실제 거부 응답 형태를 관찰하지 않고 상태코드만
보고 판정했다. 14곳 중 대다수가 공통 `classify`를 쓰고 `401 = 폐기됨`으로 판정한
것인데, 요청 자체가 잘못 만들어져 있어도(헤더 이름 오타, API 버전 누락 등) 발급처는
살아있는 키에 똑같이 401을 주므로, 그 키가 "폐기됨"으로 보고돼도 아무도 눈치채지
못하는 상태였다.

- [x] 탐지된 키를 실제 API에 **최소 권한**으로 호출해 살아있는지 확인
      (AWS `sts:GetCallerIdentity`, GitHub `GET /user`, Slack `auth.test` 등
      29개 룰 중 17개, 발급처 14곳)
- [x] 결과를 `유효 / 폐기됨 / 검증불가` 3단계로 Finding에 기록
- [x] 네트워크 호출이므로 기본 비활성 + `--validate` 플래그로 옵트인
- [x] 타임아웃/레이트리밋/오프라인 환경 처리
- [x] AWS SigV4 직접 구현 + Access Key ID ↔ Secret Access Key 짝짓기
- [x] 리포트에 키 값이 새지 않도록 에러 문자열 redact
- [x] **(1) 실패 시그니처 검사** — `classify` → `classifyWith(sig, ...)`로 교체.
      401이어도 본문이 발급처의 실제 거부 형식과 다르면 `폐기됨`이 아니라
      `검증불가 (검증기 점검 필요)`로 남긴다
- [x] **(2) 셀프체크** — `secrethound selfcheck` 추가. 형식만 맞는 가짜 키를
      14곳에 보내 표식이 여전히 유효한지 확인한다. **진짜 자격증명 불필요**.
      매주 월요일 CI([selfcheck.yml](../.github/workflows/selfcheck.yml))로 자동 실행

**실제로 발견한 것**: 셀프체크를 처음 돌려보니 14곳 **전부** 시그니처가 비어 있어
`[미확인]`이었다. 실제 API로 관찰한 응답으로 채우자 **AWS가 401이 아니라
403(`InvalidClientTokenId`)을 준다**는 것이 드러났다 — 문서만 보고 짐작했다면
놓쳤을 부분이고, 이게 정확히 이 항목이 막으려던 종류의 결함이다. 채운 뒤에는
14곳 전부 `[정상]`.

**착수 전 가정이 틀렸던 부분** — 원래 이 항목의 의의를 *"죽은 키를 걸러내는
반박 불가능한 오탐 제거"* 라고 적어놨는데, 구현하며 그게 성립하지 않는다는 걸 알았다.

폐기된 진짜 키와 **애초에 키가 아니었던 문자열은 발급처 입장에서 똑같이 401**이다.
응답만으로 이 둘을 구분할 수 없으므로 "폐기됨"은 오탐 증거가 될 수 없다.
증명되는 것은 "지금은 악용 불가"뿐이다. 게다가 히스토리에 남은 폐기 키는 여전히
"이 레포는 시크릿을 커밋한 적이 있다"는 사실을 말해주므로 리포트에서 지워서도 안 된다.

그래서 검증 결과가 신뢰도 점수를 건드리지 않도록 설계를 바꿨다.
신뢰도는 "탐지가 맞았는가", 검증은 "지금 위험한가"라는 **다른 축**이고,
하나로 합치면 폐기된 진짜 유출이 리포트에서 사라진다.
진짜 오탐 제거 효과가 있는 것은 `유효` 한 방향뿐이다.

**성공 경로 검증 — 완료 (2026-09-08)**: 무료 발급 가능한 6곳(GitHub·GitLab·
Slack·Discord·Telegram·npm) 전부를 실제 키로 확인했다.

1차 시도에서 GitHub·npm·Telegram 3곳은 바로 `유효`로 확인됐다. 나머지 3곳은
탐지 단계에서부터 걸러져 검증이 시도되지 못했는데, 원인이 서로 달랐다.

| 발급처 | 1차 실패 원인 | 결과 |
|---|---|---|
| GitLab | 최근 PAT가 `glpat-xxx.xx.xxx` 형태로 마침표를 포함하는데 룰의 문자 클래스에 마침표가 없어 통째로 안 잡힘 | **룰 버그로 확인, 수정 완료** (아래 참조) |
| Slack | 처음 붙여넣은 값에 `xoxb-` 접두사가 없었음 (Bot Token이 아닌 다른 값을 복사한 것으로 추정) | 정확한 위치(OAuth & Permissions → Bot User OAuth Token)를 안내해 재발급 → `유효` 확인 |
| npm | 64자리 hex 값으로 `npm_` 접두사가 없었음 (Granular 토큰이나 다른 화면의 값으로 추정) | Classic Token으로 재발급 지정 → `유효` 확인 |

Slack·npm은 결국 **룰 결함이 아니라 처음에 잘못된 값을 복사한 것**으로 판명됐다.
GitLab만 실제 룰 버그였다. 6곳 모두 확인 직후 폐기했다.

**GitLab PAT 룰 버그 수정 상세**: 2024년 이후 발급되는 토큰이
`glpat-<본문>.<2자 체크섬>.<나머지>` 형태로 마침표를 포함하는데, 기존 정규식은
마침표를 허용하지 않아 **통째로 탐지되지 않았다.** 오탐 필터 이전 단계에서 이미
놓치는 것이라 지금까지 나온 결함 중 가장 심각한 축에 속했다.

- [x] 정규식을 `glpat-[A-Za-z0-9\-_]{20,}(?:\.[A-Za-z0-9\-_]{2}\.[A-Za-z0-9\-_]+)?`
      로 수정 — 구형식(마침표 없는 20자)과 신형식을 모두 매칭
- [x] eval 코퍼스에 신형식 케이스 추가(`config/services.env`) — 실측이 아니었으면
      발견 못 했을 결함이라 회귀 테스트로 고정. F1 1.000·커버리지 29/29 유지

아직 확인 안 된 나머지 10곳(AWS 제외)은 사업자 인증·유료 계정이 필요해
개인 프로젝트 범위를 벗어나므로 README에 "거부 경로만 확인됨"으로 명시해 두었다.

**아직 안 된 것** — 위 10곳의 성공 경로(2xx → `유효`)는 여전히 미확인이다.
셀프체크는 가짜 키의 거부 경로만 검증하므로, 진짜 키가 있어야 확인된다.

**AWS 임시 자격증명(세션 토큰) 검증 추가 (2026-09-08)**: `aws-session-token`
룰은 원래 `aws-access-key-id`·`aws-secret-access-key`처럼 별도로 카운트되는
룰이 아니라 검증의 "재료"로만 쓰이므로, 이 작업이 **17/29라는 숫자 자체를
움직이지는 않는다** — 정직하게 밝혀두는 부분이다. 대신 이미 카운트돼 있던
`aws-access-key-id`의 실질적인 성공률을 높인다.

기존에는 임시 자격증명(`ASIA`로 시작하는 키)을 발견하면 세션 토큰이 있는지
확인도 안 하고 무조건 "STS 임시 자격증명이라 세션 토큰 없이는 검증할 수
없음"으로 포기했다 — 실제로는 `.env` 파일처럼 세 값(Access Key ID·Secret·
세션 토큰)이 나란히 유출되는 경우가 드물지 않은데도 그랬다.

- [x] `pairAWSKeys`가 Secret Access Key뿐 아니라 근처의 `aws-session-token`
      값까지 찾도록 확장 (`internal/validator/aws.go`)
- [x] `X-Amz-Security-Token` 헤더를 요청에 싣고 **SignedHeaders에도 포함**해
      서명 — AWS 문서는 서비스마다 다를 수 있다고 명시하지만, botocore를 포함한
      참조 구현들이 서명 대상에 포함시키는 쪽을 따른다 (서명이 틀리면 살아있는
      키도 SignatureDoesNotMatch로 조용히 "검증불가" 처리되므로 검증된 쪽을 택함)
- [x] 세션 토큰 값도 `redact()` 대상에 포함 — 에러 문자열에 섞여 나가지 않도록
- [x] 실제 AWS STS에 합성 임시 자격증명(ASIA + 무작위 Secret/세션 토큰)을
      보내 스모크 테스트 — `InvalidClientTokenId`로 정확히 `폐기됨` 분류됨을
      확인. 서명이 틀렸다면 `SignatureDoesNotMatch`(검증불가)가 나왔을
      것이므로, 이 결과 자체가 세션 토큰 포함 서명이 올바르다는 증거다

#### 3. baseline 파일 — 완료

이미 시크릿이 많은 레포에 도입하려면 **필수 기능**이었다. 도입 첫날 수십 건이
쏟아지고, 그 뒤로 새로 들어온 것과 원래 있던 것을 구분할 방법이 없으면 CI가
계속 빨간 상태로 남아 아무도 안 보게 된다.

- [x] `--baseline-out <path>` — 현재 탐지 결과를 baseline으로 저장
- [x] `--baseline <path>` — baseline에 있는 시크릿은 결과·검증 대상에서 제외,
      새로 생긴 것만 보고. 로드 실패 시 종료 코드 2 + `--baseline-out`으로
      먼저 만들라는 안내 메시지
- [x] 식별은 (파일 경로, 룰 ID, 시크릿 값의 SHA-256) 조합. **원본 값은 저장하지
      않는다** — baseline은 커밋되는 파일이라 원본을 넣으면 그 자체가 유출 경로가
      된다. 라인 번호는 식별에 쓰지 않아 위쪽 줄 추가/삭제나 새 커밋에도 흔들리지 않음
- [x] baseline 억제는 검증(`--validate`)보다 먼저 적용 — 이미 아는 시크릿까지
      매번 발급처에 물어보면 네트워크 호출과 레이트리밋을 의미 없이 소모하므로
- [x] `--baseline`과 `--baseline-out` 동시 사용은 명시적으로 거부 (의미가 겹쳐 혼란만 생김)
- [x] 기본 룰셋의 `exclude_paths`에 `secrethound-baseline.json` 추가 — 안 하면
      baseline 파일이 스캔 대상 안에 있을 때 자기 자신도 매번 다시 스캔됨
      (실측 중 실제로 발견한 부작용)

#### 4. 병렬 스캔 + 대형 레포 성능 수치 — 완료

기획서에 **"Go를 고른 이유가 goroutine"** 이라고 적어놨는데 구현은 전부 순차 처리였다.
문서와 구현이 어긋난 상태를 메우는 게 목적이었지, 실제로 느려서 고친 것은 아니다
(착수 전 실측에서도 express 5,678커밋을 1.4초에 처리하고 있었다).

- [x] `internal/scanner/parallel.go` — 정규식 매칭(29개 룰)을 goroutine 워커 풀에
      분산. 수집(파일 순회)과 히스토리 파싱(`git log` 출력 해석)은 그대로 한
      goroutine이 순서대로 처리하고, 그 결과로 나온 "파일 하나" 또는 "히스토리
      한 줄" 단위의 매칭만 워커에 맡긴다 — git log 파싱은 상태를 유지하며 diff
      스트림을 해석하는 작업이라 병렬화하면 정확성을 해칠 위험이 이득보다 크다고 판단
- [x] `--workers` 플래그 추가, 기본값 0(= `runtime.NumCPU()`)
- [x] 채널 기반 파이프라인(잡 채널 → 워커 N개 → 결과 채널 → 단일 수집 goroutine)으로
      뮤텍스 없이 데이터 경합을 피함. CI에 `go test -race ./internal/scanner/...`
      추가 (로컬 Windows 환경엔 cgo 툴체인이 없어 `-race`를 못 돌림)
- [x] 완료 순서가 뒤섞여도 결과가 항상 같은지 확인하는 결정성 테스트 추가
      (`TestParallelScanIsDeterministic`, 5회 반복 스캔 비교)
- [x] 실제 레포로 before/after 측정 (16코어, express.js 5,678커밋/210파일)

**측정 중 겪은 두 가지 — 둘 다 결과에 영향을 준 실수였다.**

1. **채널 버퍼 크기.** 처음엔 버퍼를 `workers*4`로 뒀는데, `workers=1`일 때
   버퍼가 4밖에 안 돼 히스토리 스캔(추가된 줄마다 잡 하나, express 기준
   115,806줄)에서 producer/consumer가 계속 서로를 깨워야 했다. 그 결과
   `workers=1`이 병렬화 이전 순차 구현(1,417ms)보다 오히려 느린 4,067ms가
   나왔다. 버퍼를 4,096으로 고정 크기로 늘리자 1,348ms로 정상화됐다.
2. **OS 파일 캐시 워밍업.** 워킹트리 스캔을 `workers=1` 먼저, `workers=0`
   나중에 측정했더니 순서 효과만으로 최대 50배 차이가 나왔다(캐시가 데워진
   쪽이 항상 빠름). 순서를 바꾸고 반복 측정해 실제 차이를 다시 쟀다.

**최종 결과 (캐시 워밍업 후 반복 측정, 3회 이상 평균)**

| 단계 | workers=1 | 자동(16코어) | 비고 |
|---|---:|---:|---:|
| 파일 트리 스캔 (express, 210파일) | ~26ms | ~11ms | 약 2배. 파일 읽기(I/O)가 겹쳐 도는 효과. 절대 시간은 원래 작음 |
| 히스토리 스캔 (express, 5,678커밋) | ~1,278ms | ~1,300ms | **차이 없음.** `git log` 서브프로세스 실행+출력 파싱이 지배적 비용이라 그 뒤 정규식 매칭을 병렬화해도 전체 시간에 거의 영향 없음 |

**정직하게 남기는 결론**: 이 기능은 "느려서 고친 것"이 아니라 "기획 문서와
구현의 불일치를 메운 것"이며, 측정해보니 그 판단이 더 뚜렷해졌다 — 정규식
매칭은 애초에 병목이 아니었고, `git log` 자체가 병목이라는 게 더 정확한
진단이다. 히스토리 스캔의 실질적인 개선이 필요해지면, 워커 풀보다 git 호출
방식 자체(예: 파일별 병렬 `git log`)를 재검토하는 쪽이 맞을 것이다.

**후속 검증 (2026-09-08)**: 위 표의 "약 2배"는 express.js를 1회 수동 클론해 잰
값이라 재현 가능한 형태로 남아있지 않았다. `internal/scanner/bench_test.go`에
저장소 밖 의존 없는 벤치마크를 추가해 다시 재봤더니, CPU 부하만 있는 조건(같은
임시 디렉토리를 반복 재사용해 파일 캐시가 데워진 상태)에서는 이득이 10~15%로
줄었다. 즉 원래 관찰한 "약 2배"는 CPU 병렬화 자체가 아니라 **콜드 캐시에서
한 파일을 매칭하는 동안 다음 파일을 디스크에서 읽어오는 I/O 오버랩** 효과였을
가능성이 크다 — 이 벤치마크 방식으로는 그 조건을 재현하지 못한다. 두 수치가
모순되는 게 아니라 서로 다른 조건(콜드 캐시 vs 웜 캐시)을 잰 것으로 해석하는
쪽이 맞다. 상세 표와 근거는 [평가지표.md](./평가지표.md)의 12번 항목 참조.

#### 5. remediation 안내 — 완료

탐지에서 끝나지 않고 대응까지 연결하는 것이 목적이다.

- [x] 키 종류별 폐기(revoke) 절차 안내 문구를 룰셋에 포함 — `config.Rule.Remediation`
      필드 추가, `rules/default.yaml`의 29개 룰 전부에 발급처별 절차(위치, URL,
      재발급 필요 여부)를 채움. `finding.Finding.Remediation`으로 그대로 실려
      JSON 리포트에도 노출됨
- [x] 히스토리에서 발견된 경우 `git filter-repo` 제거 명령 생성 —
      `finding.Finding.HistoryCleanup`, `reporter.Build()`가 `Commit != ""`인
      finding에만 채움 (`git filter-repo --path '<path>' --invert-paths`)
- [x] "키를 지우기 전에 반드시 폐기부터" 경고 — 텍스트 리포트 맨 아래
      "대응 방법" 절에서 히스토리 발견이 하나라도 있으면 항상 노출. 기존에
      `--validate`가 살아있는 키를 찾았을 때만 뜨던 경고와 달리, 검증 여부와
      무관하게 뜬다 — 폐기 전 히스토리 삭제는 검증 여부와 상관없이 위험하기 때문

**설계 결정 — 원본 값 대신 파일 단위 제거를 기본으로 안내**: `git filter-repo
--replace-text`로 정확한 값만 지우는 방법도 있었지만, 그러려면 원본 시크릿 값이
명령에 그대로 들어가야 한다. 리포트에는 마스킹된 값(`Masked`)만 싣고 원본은
직렬화하지 않는 기존 설계(`Finding.Secret`은 `json:"-"`)와 정면으로 충돌해서
채택하지 않았다. 대신 파일 전체를 히스토리에서 제거하는 `--invert-paths`를
기본으로 안내하고, 값만 지우고 싶은 사용자는 직접 `--replace-text` 규칙을
구성하도록 안내 문구만 덧붙였다.

**같은 룰·같은 파일은 한 번만**: 히스토리 스캔은 같은 시크릿이 여러 커밋에
걸쳐 나오는데, `filter/group.go`가 이미 파일+값 기준으로 묶어주므로 그 결과를
그대로 쓰면 룰별 안내 문구와 파일별 filter-repo 명령이 자연히 한 번씩만 나온다
— 별도 중복 제거 로직을 추가로 만들 필요가 없었다.

실제 레포(임시 스캐폴딩)로 워킹트리 전용/히스토리 포함 두 경로를 모두 스모크
테스트했고, 회귀 방지를 위해 `internal/reporter/reporter_test.go`에 단위
테스트 3개(룰당 한 번만 표시, 히스토리 발견 시에만 정리 명령 생성, 안내할 내용이
없으면 절 자체가 안 나옴) 추가. `go test ./...`, `go run ./eval`
(F1 1.000·커버리지 29/29 유지), `go run ./eval -history` 전부 통과 확인.

## 웹 대시보드 — 완료 (스코프 축소)

기획서의 선택 항목(v0.4)이며, 위 "확장 로드맵(차별화 근거)"과는 목적이 다르다 —
차별화 주장을 증명하는 게 아니라 이미 만든 결과를 보기 쉽게 보여주는 게 목적이다.

기획서는 웹 대시보드를 "TBD"로 남겨뒀다 — 프레임워크도 UI 스펙도 정해진 게
없었다. 처음 잡았던 추정(2~3일)은 "서버 + 실시간 스캔 트리거"까지 포함할 경우의
숫자였는데, 실제로 필요한 건 그보다 훨씬 좁았다: **이미 고정된 JSON 스키마
(`reporter.Build`)가 있으니, 그걸 읽어서 보여주기만 하면 된다.**

그래서 스코프를 의도적으로 좁혔다 — 빌드 도구도, 서버도, 프레임워크도 없는
**정적 HTML 파일 한 장**. `secrethound scan --format json --output report.json`
으로 만든 파일을 브라우저에 드래그하면 끝나는 구조.

- [x] `web/dashboard.html` — 순수 HTML/CSS/JS, 외부 의존성 없음(CDN·빌드 없음)
- [x] 파일 선택 / 드래그앤드롭으로 JSON 리포트 로드 (서버 불필요, `file://` 로
      직접 열어도 동작 — `fetch`가 아니라 `FileReader`를 쓴 이유)
- [x] 요약 카드(탐지·파일·커밋·오탐 필터·baseline·소요시간), 심각도 분포
- [x] 검증 요약 배너 — 살아있는 키가 있으면 경고, 오프라인이면 별도 안내
- [x] "대응 방법" 절 — CLI의 `reporter.writeRemediation`과 같은 로직(룰당·
      파일당 한 번만)을 JS로 재구현. `git filter-repo` 명령에 클립보드 복사 버튼 추가
- [x] 심각도 필터 칩, 경로/룰 검색, "히스토리 발견만" 토글, 컬럼 정렬
- [x] 행 클릭 시 상세 패널(설명·태그·엔트로피·검증 사유·개별 remediation) 펼침
- [x] 모든 동적 텍스트를 이스케이프 처리 — 리포트에 담긴 파일 경로·설명은
      스캔 대상 레포에서 온 신뢰할 수 없는 문자열이라 `innerHTML`에 직접 넣지 않음

**검증 방법**: Playwright(로컬에 이미 캐시된 Chromium)로 실제 브라우저에 합성
리포트를 로드해 확인 — 파일 업로드, 테이블 렌더링, 요약 카드, 대응 방법 절
표시/복사 버튼, 심각도 필터, 검색, 행 상세 펼침, 검증 배지(유효/폐기됨/검증불가
3색 구분) 전부 스크린샷으로 눈으로 확인. 콘솔 에러 없음.

**뒤로 미룬 것**: 서버 연동(레포 URL 입력 → 자동 스캔), 여러 리포트 비교(추세),
페이지네이션(현재는 findings 전체를 한 번에 렌더링 — 리포트가 수천 건 단위로
커지면 재검토 필요). 지금 스코프에서는 필요 없어서 만들지 않았다.
