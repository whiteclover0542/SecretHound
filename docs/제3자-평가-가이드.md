# 제3자 코퍼스 평가 가이드

secrethound의 정확도(Precision/Recall/F1)를 **독립된 코퍼스**로 검증해 주실 분을 위한
안내다. 여기 적힌 대로 해주시면 결과를 그대로 [평가지표.md](./평가지표.md)에 반영할 수 있다.

## 왜 필요한가

지금까지 측정된 F1 1.000([eval/README.md](../eval/README.md))은 개발자 본인이 만든
코퍼스로 잰 수치다. 코퍼스를 만든 사람이 그 코퍼스에 맞춰 룰을 고쳤으므로 구조적으로
과적합이다 — "내가 예상한 상황을 처리하는가"를 잰 것이지 일반적인 성능이 아니다.

공정하게 판단하려면 **도구를 만들지 않은 사람이, 도구를 보지 않고 만든 코퍼스**로 다시
재봐야 한다. 그게 이 문서가 부탁드리는 일이다.

## 무엇을 측정하나

| 지표 | 뜻 |
|---|---|
| Precision | 탐지한 것 중 실제로 진짜 시크릿인 비율 (오탐이 적을수록 1에 가까움) |
| Recall | 실제 시크릿 중 탐지해낸 비율 (미탐이 적을수록 1에 가까움) |
| F1 | Precision과 Recall의 조화평균 |
| 오탐(FP) 목록 | 시크릿이 아닌데 탐지된 것 — 어떤 룰이, 왜 잘못 걸렸는지 |
| 미탐(FN) 목록 | 시크릿인데 탐지되지 않은 것 — 어떤 종류를 놓쳤는지 |

오탐·미탐 **목록**이 숫자보다 중요하다. "F1 0.9" 라는 결과만으로는 무엇을 고쳐야
할지 알 수 없다. 구체적으로 어느 파일 어느 줄이 왜 틀렸는지가 있어야 룰을 고칠 수 있다.

## 코퍼스 만드는 법

### 1. 우리 코퍼스를 재사용하지 말 것

`eval/_corpus/` 는 절대 쓰지 말아 달라. 그 코퍼스로 측정하면 이미 룰이 맞춰진 상태를
다시 재는 것이라 이 평가의 의미가 없어진다. **완전히 새로 만든 코퍼스**여야 한다.

### 2. 두 종류가 섞여 있어야 한다

- **진짜 시크릿** — 형식이 맞는 API 키·토큰·개인키·DB 접속 문자열 등. 여러 서비스
  종류(AWS, GitHub, Slack, Stripe, DB 연결 문자열 등)를 섞어 주시면 좋다. 실제로
  발급된 값일 필요는 없고, **형식만 실제와 같으면** 된다 (`AKIA` + 16자 대문자/숫자처럼).
  값 자체는 만들어낸 것이어도 무방하다 — 실제 살아있는 키를 코퍼스에 넣지 않는 것을
  권장한다.
- **오탐을 유발하는 함정** — 이게 없으면 Precision을 제대로 잴 수 없다. 예:
  - 플레이스홀더 (`AKIAXXXXXXXXXXXXXXXX`, `your-api-key-here`)
  - 테스트/픽스처 코드에 있는 가짜 값
  - 해시값, UUID, base64로 인코딩된 이미지처럼 시크릿처럼 보이는 무작위 문자열
  - 공개되도록 설계된 값 (아래 "시크릿으로 치지 않는 것" 참고)

### 3. 시크릿으로 치지 않는 것 (채점 기준)

아래는 secrethound가 **의도적으로 탐지하지 않는** 것들이다. 코퍼스에 넣더라도
"탐지되어야 할 시크릿" 목록에는 넣지 말아 달라. 넣으면 정상 동작이 미탐으로
잘못 집계된다.

- 공개되도록 설계된 값: Stripe publishable key(`pk_live_...`), Google OAuth
  Client ID, SRI 무결성 해시, Sentry DSN
- 형식만 맞고 값이 명백한 플레이스홀더/더미인 경우

### 4. 정답지(레이블) 정리

채점 단위는 **(파일, 줄)** 이다. 파일별로 아래 두 목록을 정리해 주시면 된다.

- **시크릿 목록** — 파일 경로, 줄 번호, 어떤 종류인지(예: "AWS Access Key ID")
- **함정 목록** — 파일 경로, 줄 번호, 왜 시크릿이 아닌지 (선택이지만 있으면 좋음)

형식은 자유롭다. 스프레드시트, 마크다운 표, 텍스트 파일 무엇이든 상관없다.
아래처럼 간단한 표면 충분하다.

```
파일                        줄   종류               비고
config/prod.env             12   AWS Secret Key
src/notify.js                4   Slack Webhook URL
tests/fixtures/dummy.env     8   (함정) 플레이스홀더 값
```

### 5. 규모

정해진 기준은 없지만, 진짜 시크릿이 너무 적으면 한두 건만 틀려도 수치가 크게
흔들린다. 참고로 현재 자체 코퍼스는 시크릿 49건 + 함정 34건이다. 비슷하거나 더
큰 규모를 권장하지만, 시간이 부족하면 작은 규모라도 괜찮다 — 없는 것보다 훨씬 낫다.

## 실행 방법

### 준비

[Releases](https://github.com/whiteclover0542/SecretHound/releases)에서 최신
버전(현재 `v0.4.2`)을 받는다. Windows는 압축을 풀고 `secrethound.exe` 하나면 된다.

### 검사 실행

**터미널에서** 아래처럼 실행해 JSON 결과를 받아 달라 (더블클릭으로 나오는
HTML/마크다운은 사람이 보기 좋게 가공된 형태라 채점에는 JSON이 필요하다).

```bash
secrethound scan <코퍼스 경로> --format json --output result.json --exit-code=false
```

코퍼스가 git 저장소이고 히스토리 스캔(과거 커밋에서 지운 시크릿 찾기)도 확인하고
싶다면:

```bash
secrethound scan <코퍼스 경로> --history --format json --output result-history.json --exit-code=false
```

`result.json` 의 `findings` 배열에 탐지된 항목이 파일·줄·룰·신뢰도와 함께 담긴다
(원본 시크릿 값은 마스킹되어 실리지 않는다 — 안심하고 보내주셔도 된다).

### (선택) Go가 있다면 — 자동 채점

Go 툴체인이 있고 정확한 자동 채점까지 원하시면, 우리 평가 하네스에 코퍼스와
레이블을 끼워 넣어 직접 수치를 낼 수 있다. `eval/labels.yaml` 형식(`secrets`/`traps`
목록)을 참고해 레이블 파일을 같은 형식으로 만들고:

```bash
go run ./eval --corpus <코퍼스 경로> --labels <레이블 파일 경로>
```

이 방식이 번거로우면 안 하셔도 된다. 위 "실행 방법" 대로 JSON만 만들어 보내주시면
채점은 이쪽에서 한다.

## 돌려받고 싶은 것 (체크리스트)

아래 항목만 빠짐없이 있으면 형식은 자유롭다.

- [ ] 사용한 secrethound 버전 (예: `v0.4.2`, `secrethound --version` 으로 확인)
- [ ] 코퍼스 규모 (진짜 시크릿 개수, 함정 개수)
- [ ] 정답 레이블 (시크릿 목록 + 함정 목록, 파일:줄 단위)
- [ ] 검사 결과 `result.json` (그리고 있다면 `result-history.json`)
- [ ] 가능하면 **코퍼스 자체** (또는 최소한 오탐·미탐이 난 파일의 관련 부분만 발췌).
      민감한 실제 코드라 통째로 공유하기 어려우면, 오탐/미탐 목록만으로도 충분하다 —
      다만 그 경우 재현이 어려워 근거로서의 힘이 약해진다는 점은 감안해 달라

이것만 받으면 Precision/Recall/F1과 오탐·미탐 목록은 이쪽에서 계산해 정리할 수 있다.
직접 계산까지 해주신다면 더할 나위 없지만 필수는 아니다.

## (선택) gitleaks 등 다른 도구와 비교

여유가 되신다면 같은 코퍼스로 [gitleaks](https://github.com/gitleaks/gitleaks) 같은
동종 도구도 함께 돌려 비교해 주시면 좋다. 이쪽에서 만든 자체 비교(F1 1.000 vs 0.875,
[eval/README.md](../eval/README.md) 참고)는 코퍼스 편향이 있어 참고 자료 수준에
그친다고 명시해 두었다 — 제3자가 만든 코퍼스로 같은 비교를 하면 그 편향이 없어진다.
