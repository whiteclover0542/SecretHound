프로젝트가 스스로 세운 목표와 실제 측정값을 한곳에 모은 표다. 각 항목에는 재현 명령을
같이 적어서, 나중에 코드가 바뀌어 숫자가 달라지면 직접 다시 돌려서 확인할 수 있게 했다.

> 목표를 못 채운 항목도 숨기지 않고 그대로 적는다 — 그게 이 표를 만드는 목적이다.

## 상세

### 1~3. Precision / Recall / F1

**설명**: 레이블된 평가 코퍼스(`eval/_corpus`, `eval/labels.yaml`)로 탐지 정확도를 측정한다.
채점 단위는 (파일, 줄) — 한 줄에서 여러 룰이 걸려도 1건으로 센다.

**목표**: 각 지표 0.95 이상. (실무에서 오탐/미탐이 방해될 정도로 잦아지는 지점을 임의로
잡은 기준선이지, 외부에서 통용되는 표준값은 아니다.)

**재현**:
```bash
go run ./eval
```

**실측** (2026-09-09, 코퍼스: 실제 시크릿 49건 + 오탐 유발 케이스 34건):

| Precision | Recall | F1 | TP | FP | FN |
|---:|---:|---:|---:|---:|---:|
| 1.000 | 1.000 | 1.000 | 49 | 0 | 0 |

**결과**: ✅ 달성

**주의**: 이 코퍼스는 직접 만들었고, 이 코퍼스를 보면서 룰을 고쳤다. 이 수치는
"일반적인 성능"이 아니라 **회귀 방지용 기준선**으로 읽어야 한다. 자세한 한계는
[eval/README.md의 "이 숫자를 어떻게 읽어야 하나"](../eval/README.md#이-숫자를-어떻게-읽어야-하나) 참조.

### 4. 룰 커버리지

**설명**: 코퍼스에 케이스가 있어 실제로 검증된 룰의 비율. 매칭은 됐지만 오탐 필터나
중복 제거로 최종 리포트에 안 나온 룰은 검증된 것으로 보지 않는다.

**목표**: 100% (모든 룰이 최소 1개 케이스로 검증됨)

**재현**:
```bash
go run ./eval --coverage
```

**실측**: 37 / 37

**결과**: ✅ 달성

### 5. 히스토리 스캔 시나리오

**설명**: 커밋했다가 지운 시크릿, 파일째 삭제된 모듈의 시크릿 등 히스토리 스캔의 핵심
가치를 시나리오로 정의(`eval/history.yaml`)하고 기대 결과와 비교한다.

**목표**: 정의된 시나리오 전부 통과

**재현**:
```bash
go run ./eval --history
```

**실측**: 3 / 3 통과 — 상세 표는 [eval/README.md](../eval/README.md#히스토리-스캔-평가) 참조

**결과**: ✅ 달성

### 6. 실 오픈소스 레포 스캔 (과적합 검증)

**설명**: 자체 코퍼스에만 맞춰 튜닝됐을 위험을 확인하려고, 개발과 무관한 실제 공개 레포
5개(spf13/cobra, sirupsen/logrus, expressjs/express, gin-gonic/gin, pallets/flask —
합계 13,294 커밋)를 그대로 스캔했다. 잘 관리되는 레포라 실제 유출이 없어야 정상이므로,
나오는 건 대부분 오탐으로 볼 수 있다.

**목표**: 정성적 — 오탐이 소수의 명확한 원인으로 설명 가능할 것 (원인을 알 수 없는 오탐이
다수 나오면 실패로 본다)

**실측**: 오탐 4건, 원인은 2가지뿐 (Flask 문서의 예시 `SECRET_KEY`, gin 테스트 픽스처의
TLS 개인키). 상세는 [eval/README.md](../eval/README.md#실제-오픈소스-레포-스캔) 참조.

**결과**: ✅ 달성

**한계**: 이 방법으로는 미탐을 측정할 수 없다 — 해당 레포들에 애초에 진짜 유출이 없어서다
(→ 9번 참조).

### 7. gitleaks 비교

**설명**: 동일 코퍼스·동일 채점 기준으로 gitleaks v8.30.1과 비교했다.

**목표**: F1 우위

**재현** (gitleaks 설치 필요):
```bash
go run ./eval --tool gitleaks
```

**실측**: secrethound F1 1.000 vs gitleaks F1 0.875 (TP 32/28, FP 0/4, FN 0/4 — 코퍼스
버전에 따라 표본 수가 다를 수 있음, 상세는 eval/README.md 참조)

**결과**: 🟡 조건부 달성 — **비교가 구조적으로 이쪽에 유리하다.** 코퍼스를 내가 만들고
내 룰에 맞춰 고쳤으며, 코퍼스에 넣을 서비스도 내 룰셋 위주로 골랐다. "더 낫다"의 근거로
쓰려면 8번(제3자 코퍼스)이 먼저 필요하다. 자세한 비교 표는
[eval/README.md](../eval/README.md#gitleaks-비교) 참조.

### 8. 제3자 코퍼스로 재측정

**설명**: 1~3번과 7번 벤치마크의 유일한 편향 제거 방법. 공정한 비교나 일반화 가능한
정확도 주장에는 직접 만들지 않은 코퍼스가 필요하다.

**목표**: 공정한 제3자 코퍼스로 재측정

**실측**: 미실시 — 적합한 공개 코퍼스를 아직 확보하지 못함

**결과**: ❌ 미달성

**후보 경로**: [SecretBench](https://github.com/setu1421/SecretBench) — 공개 GitHub 레포
818개에서 뽑은 시크릿 후보 97,479건 중 15,084건을 사람이 직접 검증해 라벨링한 학술
데이터셋(2023, 49개 언어). 우리가 만들지 않은 코퍼스라 편향 문제를 정면으로 해결할 수
있다. 다만 라이선스 조건, 실제 접근 방법(Google BigQuery/Cloud Storage), 데이터셋
유지보수 여부를 아직 확인하지 못해 착수 전이다. 착수하면 이 항목뿐 아니라 9번(미탐 실측)도
같은 데이터셋으로 같이 풀릴 가능성이 높다.

### 9. 미탐(False Negative) 실측

**설명**: 실제로 시크릿이 유출된 적 있는 레포를 찾아 놓친 게 있는지 확인하는 것.
6번(실 오픈소스 레포 스캔)은 오탐만 볼 수 있고 미탐은 볼 수 없다 — 그 레포들에는
애초에 진짜 유출이 없어서다.

**목표**: 미탐 측정 방법 확보

**실측**: 미확보

**결과**: ❌ 미달성

**후보 경로**: 8번의 SecretBench가 "진짜 시크릿"으로 이미 라벨링된 818개 실제 레포를
제공하므로, secrethound로 그 레포들을 스캔해 라벨과 비교하면 놓친 것(FN)을 직접 셀 수
있다. 8번이 풀리면 이 항목도 같이 풀릴 가능성이 높다 — 그래서 별도 항목이지만 같은
후속 작업으로 묶어서 다룰 계획이다.

### 10~11. 키 유효성 검증기 (Validator)

**설명**: 탐지된 키를 발급처에 최소 권한으로 실제 호출해 지금도 살아있는지 확인하는
기능(`--validate`). 10번은 몇 개 룰에 검증기가 붙어 있는지, 11번은 그 검증기들이
"거부 응답"뿐 아니라 "살아있는 키 → 유효 응답"까지 실제로 확인됐는지를 본다.

**목표**:
- 10. 가능한 한 많은 룰에 검증기 연결
- 11. 개인 자격으로 무료 발급 가능한 발급처는 성공 응답(2xx → 유효)까지 실제 키로
      확인 — 거부 응답만 확인하면 "요청이 잘못 만들어져도 401이 나온다"는 구조적
      결함을 놓칠 수 있다

**재현**:
```bash
secrethound scan <repo> --validate    # 실제 검증 (네트워크 사용)
secrethound selfcheck                 # 거부 응답 시그니처만 확인 (가짜 키, 진짜 자격증명 불필요)
```

**실측**:
- 37개 룰 중 17개, 발급처 14곳에 검증기 연결 (나머지는 공개 식별자거나 형식만으로는
  살아있는지 확인할 수 없는 룰). 2026-09-08에 추가한 국내 서비스 8개 룰에는 아직
  검증기가 없어 분모만 늘었다 — 아래 '국내 룰셋 추가' 항목 참조
- 14곳 전부 거부 응답 시그니처 확인 (`selfcheck` 통과, 매주 월요일 CI 자동 실행)
- 무료로 발급 가능한 6곳(GitHub·GitLab·Slack·Discord·Telegram·npm) 전부 실제 키로
  성공 경로까지 확인

**결과**: 10 🟡 부분 달성 (17/37) · 11 ✅ 달성 (무료 발급 가능한 6/6곳)

**범위에서 제외**: 나머지 8곳(AWS·Stripe·Shopify 등)은 사업자 인증·유료 계정이 있어야
발급되는 키라 개인 프로젝트로는 성공 경로를 확인할 방법이 없다. 노력으로 풀리는
문제가 아니라서 지표에서 목표로 추적하지 않는다 — README에는 "거부 경로만 확인됨"으로
사실만 명시해 둔다.

**후속 개선 (2026-09-08, 10번 관련)**: AWS 임시 자격증명(`ASIA`로 시작하는 세션
키)을 근처의 Secret Access Key·세션 토큰과 함께 찾으면 실제로 검증을 시도하도록
확장했다. **이 작업은 17/29라는 숫자를 움직이지 않는다** — `aws-session-token`은
`aws-secret-access-key`처럼 검증의 재료로만 쓰이는 룰이라 원래도 독립적으로
카운트되지 않았기 때문이다. 대신 이미 카운트된 `aws-access-key-id`의 실질적인
성공률을 높인다: 이전에는 임시 자격증명을 발견하면 무조건 포기했는데, 이제는
세 값이 함께 유출된 경우(`.env` 파일 등) 실제로 검증을 시도한다. 실제 AWS STS에
합성 임시 자격증명을 보내 `InvalidClientTokenId`로 정확히 분류됨을 확인했다 —
서명이 틀렸다면 `SignatureDoesNotMatch`(검증불가)만 나왔을 것이므로, 이 결과 자체가
세션 토큰을 포함한 서명이 올바르다는 증거다. 상세는 `progress.md`의 "키 유효성
검증(Validator)" 절 참조.

### 12. 병렬 스캔 성능 (파일 트리)

**설명**: 정규식 매칭을 워커 풀로 분산했을 때(`--workers`) `workers=1` 대비 실제로
빨라지는지 확인한다.

**목표**: `workers=1` 대비 유의미한 개선

**재현** (저장소 밖 레포에 의존하지 않는 재현 가능한 벤치마크, 이번에 새로 추가):
```bash
go test ./internal/scanner/... -run '^$' -bench BenchmarkScanWorktree -benchtime=5x
```
(`internal/scanner/bench_test.go`. 이전까지는 express.js를 수동으로 클론해 1회성으로
측정한 수치만 있었다 — 그 결과가 `progress.md`의 "병렬 스캔" 절에 남아있다.)

**실측** (2026-09-08, 800파일×400줄, 16코어, 5회 반복 평균): workers=1 2,130ms,
자동(16코어) 1,869ms — 약 14%

**결과**: 🟡 부분 달성 — 개선은 실재하지만, 이전에 기록한 "약 2배"에는 한참 못
미친다. **원래 측정이 재현되지 않는 이유는 조사해서 밝혀냈다**: 이 벤치마크는
같은 임시 디렉토리를 반복 재사용해 OS 파일 캐시가 데워진 상태로 돈다. 반면 원래
측정은 방금 클론한 실제 express.js 레포(콜드 캐시)를 대상으로 했다 — 그 조건에서는
이득이 CPU 병렬화가 아니라 "한 파일을 매칭하는 동안 다음 파일을 디스크에서 읽어오는"
I/O 오버랩에서 왔을 가능성이 크다(Windows에서는 파일 열기마다 붙는 백신 스캔
오버헤드가 이 효과를 키웠을 수도 있다). 즉 **워커 풀은 CPU 바운드 상황에서 10~15%,
콜드 캐시의 I/O 바운드 상황에서는 그보다 훨씬 크게** 기여하는 것으로 보이며, 두
수치 모두 거짓은 아니고 서로 다른 조건을 재고 있었다.

**범위 밖 — 히스토리 스캔 병렬화는 애초에 목표가 성립하지 않음**: 처음엔 이
항목을 파일 트리(12번)와 나란히 "히스토리 스캔도 workers=1 대비 유의미한 개선"
으로 뒀었다. 그런데 히스토리 스캔은 `git log` 서브프로세스 실행+출력 파싱이
지배적 비용이고, 병렬화한 건 그 뒤에 오는 정규식 매칭뿐이다 — 병목을 아예
건드리지 않으므로 애초에 개선될 수 없는 구조다. 실측(workers=1 570ms vs 자동
542ms, 150커밋, 차이 없음)은 "미달성"이 아니라 "정규식이 이 경로의 병목이
아니었다"를 재확인한 것에 가깝다. 그래서 목표 항목에서 아예 뺐다 —
"미달성(❌)"으로 세면 애초에 불가능한 일을 실패로 기록하는 셈이 되기 때문이다.
재현: `go test ./internal/scanner/... -run '^$' -bench BenchmarkScanHistory -benchtime=5x`.
